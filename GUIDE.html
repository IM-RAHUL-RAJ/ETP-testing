3. Open the ports

Runs in: AWS console

In the instance's security group, add inbound TCP rules for 4200, 3000 and 8085. Limiting the source to your own IP is safer than opening them to everyone. Leave 5432, 9092 and 8083 closed; only containers use them.

Build and run

Runs in: EC2 box, in the session, inside ETP-testing

docker-compose up --build -d

--build rebuilds the images so code changes take effect. -d runs the containers in the background, so they keep running after the session closes. Without -d the session is tied up by the logs.

On a box with little memory, build one image at a time:

COMPOSE_PARALLEL_LIMIT=1 docker-compose build
docker-compose up -d

Check it

docker-compose ps                 # every service Up, healthy where a check exists
curl -s -o /dev/null -w "%{http_code}\n" localhost:4200/      # 200
curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/docs  # 200
docker-compose logs -f            # follow logs; Ctrl+C stops watching only
docker-compose down               # stop and remove the containers

Then open http://<public-ip>:4200 in a browser, register, log in and place an order. The full curl walk-through of the trading flow, including database checks, is in flow.md.

Containers do not come back after a reboot unless each service has restart: unless-stopped, which is not set today.

Why the public IP needs four settings

Everything worked on the development box with no settings, then Register failed on EC2. The reason is the same for all four settings: the browser is now on a different machine from the containers.

Wrong address: AUTH_URL and BACKEND_URL

The frontend writes two addresses into every page it sends. Unset, they default to http://localhost:3000 and http://localhost:8085. In a browser, localhost means the laptop, where nothing is listening.

Closed ports: 3000 and 8085

Only :4200 is typed in the address bar, but the frontend container is not a middleman. The JavaScript in the browser calls the auth service and the trade API directly, so each needs its own inbound rule.

CORS: CORS_ALLOWED_ORIGINS

A page from port 4200 calling port 8085 is "cross-origin". The service being called decides which page addresses it accepts, so this is a backend setting. The auth service already accepts any page address. The trade API had localhost:4200 fixed in its code; it now reads the list from this setting. The value is the address of the page, not of the API.

Cookie: COOKIE_SECURE=false

Login issues a 15-minute access token and a long-lived refresh cookie. Browsers store a cookie marked Secure only over https, with an exception for localhost. Over http://<public-ip> the cookie is dropped and the session ends when the token expires.

Cost of the flag. With it off, the refresh cookie crosses the internet unencrypted. That is acceptable for a short-lived test box with test accounts, not for real users. The proper fix is https, which the EKS setup provides.

Nothing changed inside the Docker network. Containers still reach each other by service name (postgres, kafka:29092). Only the addresses handed to the browser changed.

Test the application against RDS before containers

Before the database goes behind Kubernetes, check that the application can use it at all. Run the services directly on a machine (no Docker, no cluster), pointed at RDS. If something is wrong with the address, the password, the schema or encryption, it shows up here, where there is only one thing to debug.

Status. In this project the database was made public on 4 October and tested from the EC2 box and from a pod. The local run of the services described in steps 2 and 3 is the recommended check and was not carried out as part of that history.

1. Make the database public, for your machine only

Runs in: EC2 box or CloudShell

A new RDS instance is private: only machines inside its own VPC can reach it. To test from a laptop or any machine outside that VPC, give it a public address first, and allow only the testing machine's IP in its security group.

REGION=ap-south-1
RDS_SG=sg-0fc2ee1301e173d37

aws rds modify-db-instance --db-instance-identifier database-1 --publicly-accessible --apply-immediately --region $REGION --query 'DBInstance.DBInstanceStatus' --output text
aws rds wait db-instance-available --db-instance-identifier database-1 --region $REGION
aws rds describe-db-instances --db-instance-identifier database-1 --region $REGION --query 'DBInstances[0].PubliclyAccessible'

# allow one address: the public IP of the machine you test from
MY_IP=<public IP of the testing machine>      # on that machine: curl -s https://checkip.amazonaws.com
aws ec2 authorize-security-group-ingress --group-id $RDS_SG --protocol tcp --port 5432 --cidr $MY_IP/32 --region $REGION

The wait prints nothing for a few minutes while the database is Modifying. The third command must print true. Never use 0.0.0.0/0 as the source: port 5432 is scanned constantly.

The same thing in the console: RDS, database-1, Modify, Connectivity, Additional configuration, Publicly accessible. Then EC2, Security Groups, the database's group, Edit inbound rules, add PostgreSQL from My IP.

From the EC2 box no public address is needed, because the box is in the database's VPC. There only the rule for 172.31.0.0/16 is required.

2. How the application picks its database

Nothing in application.yml has to be edited. Every database value is an environment variable with a local default after the colon:

# sprint8/src/main/resources/application.yml (trade-api) and executor/src/main/resources/application.yml
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:trading_system_db}?currentSchema=trading
    username: ${DB_USER:postgres}
    password: ${DB_PASSWORD:...}

With no variables set, the services use Postgres on localhost. Set the five variables and the same build talks to RDS. The auth service reads the same five names in src/config/configuration.ts.

RDS for PostgreSQL 18 accepts only encrypted connections. The Java services encrypt on their own. The Node auth service does not unless told to, which is what PGSSLMODE=no-verify does: encrypt, without checking the server certificate.

Store the images in ECR

Runs in: EC2 box, in the session, inside ETP-testing

Kubernetes cannot use images that exist only on the box. They go to Amazon ECR, the AWS image registry, and the deployment files pull them from there. Postgres and Kafka use public images and stay out of ECR.

1. Set the variables

Variables last only as long as the session. Run this block again after every reconnect, before any other command here.

REGION=ap-south-1
TAG=1.0
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REGISTRY=$ACCOUNT.dkr.ecr.$REGION.amazonaws.com
echo $REGISTRY

The echo must print an address that starts with the 12-digit account number.

2. Create the repositories (once)

for s in auth-service trade-api executor frontend; do
  aws ecr create-repository --region $REGION --repository-name trading-$s
done

They can also be created in the console under ECR, Create repository, with the names trading-auth-service, trading-trade-api, trading-executor and trading-frontend.

3. Log Docker in to ECR

aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $REGISTRY

Nothing is typed in. The username is always the word AWS, and the password is a temporary token the first command creates from the box's role and passes straight to Docker. This step is needed even on an EC2 box: the aws command uses the role automatically, but docker push is a separate program and does not. The token lasts 12 hours.

4. Tag and push

docker-compose names the images it builds etp-testing-<service>:latest. Tagging gives each one its ECR address; pushing uploads it.

docker images | grep etp-testing

for s in auth-service trade-api executor frontend; do
  docker tag etp-testing-$s:latest $REGISTRY/trading-$s:$TAG
  docker push $REGISTRY/trading-$s:$TAG
done

5. Check

for s in auth-service trade-api executor frontend; do
  aws ecr list-images --region $REGION --repository-name trading-$s --query 'imageIds[].imageTag' --output text
done

Each line should print 1.0. In the deployment files the image is then <REGISTRY>/trading-<name>:1.0.

When the code changes

Rebuild the one service that changed and push it to the same repository under a new tag. No new repository is needed, and only the changed layers are uploaded.

docker-compose build frontend
docker tag etp-testing-frontend:latest $REGISTRY/trading-frontend:1.1
docker push $REGISTRY/trading-frontend:1.1

Then change that service's tag in its deployment file from 1.0 to 1.1 and apply it. Use a new tag every time instead of pushing over 1.0: the manifests use imagePullPolicy: IfNotPresent, so a node that already holds 1.0 would keep running the old image, and a new tag keeps rollback possible.

2. Give the box's role access to the cluster

Session Manager and EKS are two separate things. Session Manager only gives you a terminal on the EC2 box. kubectl is a program on that box that sends requests over the network to the cluster's API server, and the cluster decides for itself whether to accept them.

The cluster asks two questions on every request:

  1. Who are you? kubectl answers with the AWS identity of whatever is running it. On the box that is the box's IAM role, capstone-instance. This is not your console login.
  2. Are you on my list, and what may you do? A new cluster's list contains only the identity that created it. An access entry adds another identity to the list, and its access policy says what that identity may do.

So the access entry does not connect the EC2 box to the cluster as a machine. It tells the cluster: requests signed by the role capstone-instance are allowed, with administrator rights. Any machine using that role gets the same access.

Runs in: EC2 box, then AWS console

aws sts get-caller-identity --query Arn --output text

This prints the session ARN. The console needs the role ARN, which is a different form of the same thing:

ARN

What to enterarn:aws:iam::<account>:role/capstone-instance

sts becomes iam, assumed-role/ becomes role/, and the /i-... ending is dropped.

Add the disk add-on

Runs in: EC2 box, in the session

A pod's own storage is temporary: when the pod restarts, everything it wrote is gone. Kafka holds messages that must survive a restart, so it needs a real disk that lives outside the pod. On AWS that disk is an EBS volume.

The idea: a claim and something to answer it

A pod cannot create an EBS volume itself. It can only file a request, called a claim: "I need 2 GB of type gp3". Something in the cluster has to notice that claim, ask AWS to create the volume, attach it to the node the pod runs on, and hand it to the pod. That something is the EBS CSI driver, and on EKS it is installed as an add-on.

The cluster did not have it: aws eks list-addons showed only coredns, kube-proxy, metrics-server and vpc-cni. The gp2 storage class that was listed does not work on Kubernetes 1.34 without the driver.

Without the add-on the damage spreads. Kafka never starts. The order service and the executor each wait for Kafka's topics before starting, so they never start either. Only the frontend and auth service would come up: the page would load and login would work, but nothing to do with orders.

Why a policy is attached to the node role

Creating and attaching a volume are calls to AWS, and AWS only accepts calls from an identity that is allowed to make them. The add-on runs on the worker nodes and uses the nodes' IAM role. AmazonEBSCSIDriverPolicy gives that role permission to create, attach and delete EBS volumes. Without it the add-on would be installed but every disk request would be refused by AWS.

Commands

REGION=ap-south-1

# the IAM role the worker nodes use
NODE_ROLE=$(aws eks describe-nodegroup --cluster-name capstone --nodegroup-name workers --region $REGION --query 'nodegroup.nodeRole' --output text | awk -F/ '{print $NF}')
echo $NODE_ROLE

# let that role create and attach EBS volumes, then install the add-on
aws iam attach-role-policy --role-name $NODE_ROLE --policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
aws eks create-addon --cluster-name capstone --addon-name aws-ebs-csi-driver --region $REGION

# after about two minutes
aws eks describe-addon --cluster-name capstone --addon-name aws-ebs-csi-driver --region $REGION --query 'addon.status' --output text
kubectl get pods -n kube-system | grep ebs

Expected: ACTIVE, two ebs-csi-controller pods and one ebs-csi-node pod per node, all Running.

The add-on is free. The only disk it will create is Kafka's 2 GB gp3 volume, a few cents a month. The analytics disk was removed because this deployment does not use analytics.

Connect the cluster to the RDS database

On the EC2 box, Postgres was a container. On EKS the database is an RDS instance, so three things are needed: the pods must be able to reach it over the network, its firewall must let them in, and it must contain the schema.

The idea: two networks and one firewall

A VPC is a private network inside AWS. Machines in the same VPC can talk to each other on private addresses. Machines in different VPCs cannot, unless something joins the two.

This setup has two VPCs. The EC2 box and the database are in the account's default VPC (172.31.0.0/16). eksctl created a brand new VPC for the cluster (192.168.0.0/16). So the box could reach the database from the start, and the pods could not.

A security group is the firewall on a single resource. The database's security group lists which addresses may connect to port 5432. Being on a connected network is not enough; the address must also be on that list.

VPC peering is a private link between two VPCs. With it, and a route on each side saying "traffic for the other network goes through the link", machines in one VPC reach machines in the other on private addresses, without touching the internet.

Why peering, not a public database

Both were tried. The database was first made public (see Test the application against RDS before containers) with one security group rule per node. That worked, but it has a flaw: each rule names one node's public IP, and a node that is replaced or added gets a new IP that is not on the list. It was then replaced by peering.

Public database + node IPsVPC peering + one range rule (in use)
Security group ruleOne per node public IPOne for 192.168.0.0/16, the cluster's whole network
A node is replaced or addedIts pods lose the database until its IP is added by handKeeps working: every node and pod always has an address in that range
Database exposureHas a public address; safety rests on the rules being rightNo public address at all
Traffic pathOver the internetStays inside AWS on private addresses
SetupOne setting and a few rulesA peering connection, routes on both sides, one rule; done once
CostNoneNone

In short, peering is set up once and then needs no attention, and the database is not reachable from the internet.

1. Let the box in, then create the database and load the schema

Runs in: EC2 box, inside ETP-testing

docker-compose loaded the schema automatically by mounting the two SQL files into the Postgres container. On RDS it is done once by hand. psql is run from the Postgres image already on the box, so nothing is installed.

REGION=ap-south-1
RDS_SG=sg-0fc2ee1301e173d37
export PGHOST=database-1.c94cwk4g097q.ap-south-1.rds.amazonaws.com
export PGPASSWORD='<master password>'

# the box's network may connect on 5432
aws ec2 authorize-security-group-ingress --group-id $RDS_SG --protocol tcp --port 5432 --cidr 172.31.0.0/16 --region $REGION

P="docker run --rm -i -e PGPASSWORD -e PGSSLMODE=require postgres:16-alpine psql -h $PGHOST -U postgres -v ON_ERROR_STOP=1"
$P -d postgres -c "CREATE DATABASE trading_system_db"
$P -d trading_system_db < sprint8/db/schema.sql
$P -d trading_system_db < sprint8/db/seed-data.sql
$P -d trading_system_db -c "select table_schema, count(*) from information_schema.tables where table_schema in ('auth','trading') group by 1"

Expected at the end: trading with 4 tables and auth with 2.

2. Join the two VPCs

Runs in: EC2 box, in the session

EKS_VPC=vpc-0d0ed4c712f06dcec
RDS_VPC=vpc-084b301c91f11db96
EKS_CIDR=$(aws ec2 describe-vpcs --vpc-ids $EKS_VPC --region $REGION --query 'Vpcs[0].CidrBlock' --output text)
RDS_CIDR=$(aws ec2 describe-vpcs --vpc-ids $RDS_VPC --region $REGION --query 'Vpcs[0].CidrBlock' --output text)
echo "cluster $EKS_CIDR   database $RDS_CIDR"

# the link
PCX=$(aws ec2 create-vpc-peering-connection --vpc-id $EKS_VPC --peer-vpc-id $RDS_VPC --region $REGION --query 'VpcPeeringConnection.VpcPeeringConnectionId' --output text)
aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id $PCX --region $REGION --query 'VpcPeeringConnection.Status.Code' --output text

# routes in both directions, in every route table
for rt in $(aws ec2 describe-route-tables --region $REGION --filters Name=vpc-id,Values=$EKS_VPC --query 'RouteTables[].RouteTableId' --output text); do
  aws ec2 create-route --region $REGION --route-table-id $rt --destination-cidr-block $RDS_CIDR --vpc-peering-connection-id $PCX
done
for rt in $(aws ec2 describe-route-tables --region $REGION --filters Name=vpc-id,Values=$RDS_VPC --query 'RouteTables[].RouteTableId' --output text); do
  aws ec2 create-route --region $REGION --route-table-id $rt --destination-cidr-block $EKS_CIDR --vpc-peering-connection-id $PCX
done

# one rule for the whole cluster network
aws ec2 authorize-security-group-ingress --group-id $RDS_SG --protocol tcp --port 5432 --cidr $EKS_CIDR --region $REGION

What each part does:

  • Peering connection. One side requests the link, the other accepts it. Both VPCs are in the same account here, so both commands run from the same place. The status prints provisioning and becomes active within seconds.
  • Routes. A link alone carries nothing. Each network needs an entry saying that addresses of the other network are reached through the link. Here that was six route tables in total.
  • Security group rule. The database's firewall now accepts port 5432 from any address in the cluster's network.

The two ranges must not overlap for peering to work. Here they are 192.168.0.0/16 and 172.31.0.0/16.

3. Keep the database private

While a database is public, its name resolves to the public address from outside its own VPC, so pods would go around the link. Private, the name always resolves to the private address.

aws rds modify-db-instance --db-instance-identifier database-1 --no-publicly-accessible --apply-immediately --region $REGION --query 'DBInstance.DBInstanceStatus' --output text
aws rds wait db-instance-available --db-instance-identifier database-1 --region $REGION
aws rds describe-db-instances --db-instance-identifier database-1 --region $REGION --query 'DBInstances[0].PubliclyAccessible'

The last command must print false. If the database was never made public, this step changes nothing.

Because the public route was used first, its two node rules were left behind and should be removed:

for ip in 3.110.221.216 65.0.129.241; do
  aws ec2 revoke-security-group-ingress --group-id $RDS_SG --protocol tcp --port 5432 --cidr $ip/32 --region $REGION
done

4. Test from inside the cluster

kubectl run pgtest --restart=Never --image=postgres:16-alpine -- pg_isready -h $PGHOST -p 5432 -t 10
sleep 15
kubectl logs pgtest
kubectl delete pod pgtest

Expected: accepting connections. This starts a throwaway pod on a node and asks the database whether it is listening. Run it after step 3 has printed false and the node rules are gone; a pass then proves the traffic went through the peering link. This was confirmed on 4 October with the database private and the node rules removed.

Password. The master password in use is weak. The database is no longer reachable from the internet, but anything inside either VPC can try it. Change it with aws rds modify-db-instance --master-user-password and update the Kubernetes secret to match.

Known limit of four separate load balancers

Each load balancer has its own hostname. Over plain http the browser will not send the refresh cookie from the frontend's hostname to the auth service's hostname, so a login lasts until the 15-minute access token expires. One shared entry point with https removes this.
