At a glance

The trading platform (four application services plus Postgres and Kafka) now runs with docker-compose on one EC2 box and is usable from a browser at the box's public IP. Its four application images are stored in ECR, ready for Kubernetes. This page is the whole path to that point, in the order it has to be done.

What the AWS account allows

The account has a guardrail policy (CapstoneGuardrails) that only blocks things. Anything it does not block still needs to be granted by the second policy, CapstoneIamAccess, which has not been reviewed.

AreaAllowedBlocked
EC2 instance typest3.micro, t3.small, t3.medium, t3.large, m5.large, m5.xlarge, m6i.large, m6i.xlargeEvery other type: GPU, Graviton (t4g, m6g), anything above xlarge
RDS classesdb.t4g.micro, db.t4g.small, db.t4g.medium, db.t4g.large, db.m6g.largeEvery other class
Account and auditLeaving the organisation, changing account contacts, editing the two Capstone policies, stopping or changing CloudTrail

The EC2 rule looks only at the instance type. It applies the same way to Amazon Linux, Red Hat, Ubuntu and Windows, and to the worker nodes of an EKS cluster. There is no limit on region or on the number of instances.

Connect to the box

There is no .pem key. Access is through AWS Session Manager.

From the AWS console

Runs in: AWS console

  1. Set the region to Asia Pacific (Mumbai).
  2. EC2, Instances, select the instance.
  3. Connect, Session Manager tab, Connect. A terminal opens in a new tab.
  4. Become root for the install steps: sudo su -

From the Windows VM

Runs in: Windows VM, CMD

The Windows VM is itself an EC2 instance in a different AWS account, so the CLI uses that VM's role by default and is refused. A named profile with your own credentials fixes that.

  1. Install the AWS CLI and the Session Manager plugin. Downloading the plugin installer is not enough: run it, then open a new CMD window.
  2. Create an access key for your IAM user in the capstone account and save it as a profile:
aws configure --profile capstone
set AWS_PROFILE=capstone
aws sts get-caller-identity
aws ssm start-session --target i-0fc99e68e7d4fa5ff --region ap-south-1

List the instances

Runs in: CloudShell or Windows VM

aws ec2 describe-instances --region ap-south-1 --query "Reservations[].Instances[].[InstanceId,Tags[?Key=='Name']|[0].Value,State.Name,InstanceType]" --output table

Install the tools on the box

Runs in: EC2 box, in the session (Amazon Linux 2023)

Four installs, in this order. Each block ends with a check.

1. git

sudo dnf install -y git
git --version

2. Docker

sudo dnf install -y docker
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
docker --version

The group change applies to new logins. Reconnect, or keep using sudo or root.

3. docker-compose (the hyphenated command)

sudo curl -SL "https://github.com/docker/compose/releases/latest/download/docker-compose-linux-$(uname -m)" -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose
docker-compose --version

4. buildx

Amazon Linux's Docker package does not include it, and Compose refuses to build without it.

VER=$(curl -fsSL -o /dev/null -w '%{url_effective}' https://github.com/docker/buildx/releases/latest | sed 's#.*/tag/##')
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -SL "https://github.com/docker/buildx/releases/download/${VER}/buildx-${VER}.linux-amd64" -o /usr/local/lib/docker/cli-plugins/docker-buildx
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-buildx
docker buildx version

On Ubuntu, replace the first two blocks with sudo apt update && sudo apt install -y git docker.io. On Red Hat, dnf install docker gives Podman; add Docker's own repository first.

Get the code and configure it

Runs in: EC2 box, in the session

1. Clone, or pull if the folder exists

git clone https://github.com/IM-RAHUL-RAJ/ETP-testing.git
cd ETP-testing
git pull origin main

2. Create .env

.env is never committed, so a fresh clone only has .env.example. Copy it, then set six values. Replace the IP if the box's public IP has changed, and put in the real Fauxnance key.

cp .env.example .env

sed -i \
  -e 's|^AUTH_URL=.*|AUTH_URL=http://13.201.4.242:3000|' \
  -e 's|^BACKEND_URL=.*|BACKEND_URL=http://13.201.4.242:8085|' \
  -e 's|^CORS_ALLOWED_ORIGINS=.*|CORS_ALLOWED_ORIGINS=http://13.201.4.242:4200|' \
  -e 's|^COOKIE_SECURE=.*|COOKIE_SECURE=false|' \
  -e 's|^FAUXNANCE_API_KEY=.*|FAUXNANCE_API_KEY=<your fnx_dev_ key>|' \
  -e 's|^FAUXNANCE_BASE_URL=.*|FAUXNANCE_BASE_URL=https://y4t9nq2bqf.execute-api.eu-west-2.amazonaws.com/v1|' \
  .env

3. Open the ports

Runs in: AWS console

In the instance's security group, add inbound TCP rules for 4200, 3000 and 8085. Limiting the source to your own IP is safer than opening them to everyone. Leave 5432, 9092 and 8083 closed; only containers use them.

Build and run

Runs in: EC2 box, in the session, inside ETP-testing

docker-compose up --build -d

--build rebuilds the images so code changes take effect. -d runs the containers in the background, so they keep running after the session closes. Without -d the session is tied up by the logs.

On a box with little memory, build one image at a time:

COMPOSE_PARALLEL_LIMIT=1 docker-compose build
docker-compose up -d

Check it

docker-compose ps                 # every service Up, healthy where a check exists
curl -s -o /dev/null -w "%{http_code}\n" localhost:4200/      # 200
curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/docs  # 200
docker-compose logs -f            # follow logs; Ctrl+C stops watching only
docker-compose down               # stop and remove the containers

Then open http://<public-ip>:4200 in a browser, register, log in and place an order. The full curl walk-through of the trading flow, including database checks, is in flow.md.

Containers do not come back after a reboot unless each service has restart: unless-stopped, which is not set today.

Why the public IP needs four settings

Everything worked on the development box with no settings, then Register failed on EC2. The reason is the same for all four settings: the browser is now on a different machine from the containers.

Wrong address: AUTH_URL and BACKEND_URL

The frontend writes two addresses into every page it sends. Unset, they default to http://localhost:3000 and http://localhost:8085. In a browser, localhost means the laptop, where nothing is listening.

Closed ports: 3000 and 8085

Only :4200 is typed in the address bar, but the frontend container is not a middleman. The JavaScript in the browser calls the auth service and the trade API directly, so each needs its own inbound rule.

CORS: CORS_ALLOWED_ORIGINS

A page from port 4200 calling port 8085 is "cross-origin". The service being called decides which page addresses it accepts, so this is a backend setting. The auth service already accepts any page address. The trade API had localhost:4200 fixed in its code; it now reads the list from this setting. The value is the address of the page, not of the API.

Cookie: COOKIE_SECURE=false

Login issues a 15-minute access token and a long-lived refresh cookie. Browsers store a cookie marked Secure only over https, with an exception for localhost. Over http://<public-ip> the cookie is dropped and the session ends when the token expires.

Cost of the flag. With it off, the refresh cookie crosses the internet unencrypted. That is acceptable for a short-lived test box with test accounts, not for real users. The proper fix is https, which the EKS setup provides.

Nothing changed inside the Docker network. Containers still reach each other by service name (postgres, kafka:29092). Only the addresses handed to the browser changed.

Store the images in ECR

Runs in: EC2 box, in the session, inside ETP-testing

Kubernetes cannot use images that exist only on the box. They go to Amazon ECR, the AWS image registry, and the deployment files pull them from there. Postgres and Kafka use public images and stay out of ECR.

How ECR differs from JFrog

JFrogECR
What a repository isA folder holding many different imagesOne image, with all its versions
The four imagesOne repository, four images insideFour repositories, one per image
Image address<host>/<repo-key>/trading-frontend:1.0<account>.dkr.ecr.ap-south-1.amazonaws.com/trading-frontend:1.0
LoginJFrog user and access tokenThe box's AWS role; no separate password
Pulling from EKSNeeds a pull secretNo secret needed in the same account

1. Set the variables

Variables last only as long as the session. Run this block again after every reconnect, before any other command here.

REGION=ap-south-1
TAG=1.0
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REGISTRY=$ACCOUNT.dkr.ecr.$REGION.amazonaws.com
echo $REGISTRY

The echo must print an address that starts with the 12-digit account number.

2. Create the repositories (once)

for s in auth-service trade-api executor frontend; do
  aws ecr create-repository --region $REGION --repository-name trading-$s
done

They can also be created in the console under ECR, Create repository, with the names trading-auth-service, trading-trade-api, trading-executor and trading-frontend.

3. Log Docker in to ECR

aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $REGISTRY

Nothing is typed in. The username is always the word AWS, and the password is a temporary token the first command creates from the box's role and passes straight to Docker. This step is needed even on an EC2 box: the aws command uses the role automatically, but docker push is a separate program and does not. The token lasts 12 hours.

4. Tag and push

docker-compose names the images it builds etp-testing-<service>:latest. Tagging gives each one its ECR address; pushing uploads it.

docker images | grep etp-testing

for s in auth-service trade-api executor frontend; do
  docker tag etp-testing-$s:latest $REGISTRY/trading-$s:$TAG
  docker push $REGISTRY/trading-$s:$TAG
done

5. Check

for s in auth-service trade-api executor frontend; do
  aws ecr list-images --region $REGION --repository-name trading-$s --query 'imageIds[].imageTag' --output text
done

Each line should print 1.0. In the deployment files the image is then <REGISTRY>/trading-<name>:1.0.

When the code changes

Rebuild the one service that changed and push it to the same repository under a new tag. No new repository is needed, and only the changed layers are uploaded.

docker-compose build frontend
docker tag etp-testing-frontend:latest $REGISTRY/trading-frontend:1.1
docker push $REGISTRY/trading-frontend:1.1

Then change that service's tag in its deployment file from 1.0 to 1.1 and apply it. Use a new tag every time instead of pushing over 1.0: the manifests use imagePullPolicy: IfNotPresent, so a node that already holds 1.0 would keep running the old image, and a new tag keeps rollback possible.

To confirm an out-of-memory freeze

# from CloudShell, works while the box is frozen
aws ec2 get-console-output --instance-id <id> --region ap-south-1 --latest --output text | grep -i -E "out of memory|oom|killed process"
# from inside, after reconnecting
sudo dmesg -T | grep -i -E "out of memory|oom|killed process"
free -h

A box with no swap can freeze without logging anything, so an empty result does not rule it out.

Still open

  • No https. The box is plain http with COOKIE_SECURE=false. Fine for testing only.
  • No Elastic IP. A stop and start changes the public IP; update the three address lines in .env and run docker-compose up -d again.
  • No auto-restart. After a reboot, run docker-compose up -d by hand.
  • Default secrets. .env.example ships default database and JWT values; change them for anything beyond testing.
  • First box. ec2-s144 is unused; terminate it if it is still running.
  • Manifests still point at JFrog. k8s/ and k8s-tester/ use a JFrog registry address and a pull secret; both change to the ECR address, with no secret, in the Kubernetes step.
  • EKS. Next step, not started on this account.
