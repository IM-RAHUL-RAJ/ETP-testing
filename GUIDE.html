The ready-made files: CD2026-files

The rest of this page records how one repository, ETP-testing, was deployed, with files written for it as it went. Those files have since been made generic and collected in one repository, CD2026-files, so another project does not write its own Dockerfiles, compose file, Kubernetes files or pipeline. It copies one folder, fills in one file, and runs the same steps.

Every AWS step on this page (the box, Session Manager, the tools, the cluster access, the disk add-on, VPC peering, Jenkins) applies to any project as written. This section gives the repository-specific commands that replace the ETP-testing ones.

Status on 7 October. The docker phase was run from start to finish on the development box with the team5 repository: the four images build from the generic Dockerfiles, every container comes up healthy, the SQL loads, and onboarding, the sign-up email, registration, login and a call with a token were checked with curl. test.sh was run, and load-schema.sh was run against a plain Postgres. The Kubernetes files and deploy.sh were produced and checked in a dry run, but in this generic form they have not been applied to a cluster; they are adapted from the files that deployed ETP-testing. Not checked: the page in a real browser, an order being filled, load-schema.sh against RDS, and anything on EKS.

3. One change in an Angular frontend

A Flask frontend reads its settings every time it builds a page. An Angular application is compiled into static JavaScript files once, when the image is built, and the browser runs them: there is no server-side code to read a setting later. If the API addresses are compiled in, the image only works on the machine it was built for.

The kit's Angular image keeps the addresses out of the build. When the container starts, it writes them into a small file, /app-config.js, from AUTH_URL and BACKEND_URL. The application has to load that file and prefer its values, which is two small edits, made once:

<!-- src/index.html, inside <head> -->
<script src="app-config.js"></script>

// where the API base addresses are defined
const runtime = (globalThis as any).__APP_CONFIG__ ?? {};
export const authBaseUrl  = runtime.authBaseUrl  ?? 'http://localhost:3000';
export const tradeBaseUrl = runtime.tradeBaseUrl ?? 'http://localhost:8081';

Add an app-config.js containing window.__APP_CONFIG__ = {}; to the folder Angular copies as it is (public/), so npm start on a laptop finds the file and falls back to the built-in addresses. With both settings empty, the page calls the address it was loaded from, which is what the single load balancer on EKS needs. This is the mechanism in How the addresses changed without changing code, with the value read when the container starts.

Three things differ from the ETP-testing files:

  • Pods take every setting at once. Each Deployment says "all of app-config and all of app-secrets" instead of listing settings one by one, so the files do not depend on what the code calls them.
  • One load balancer from the start. There is no four-load-balancer stage and no set-urls.sh. The frontend's two addresses are empty, and deploy.sh writes the load balancer's address into any setting that used {frontend_url} or {cors_origins}.

This replaces the sed block in Get the code and configure it, step 2, for the four address settings. The script works out CORS_ALLOWED_ORIGINS from the frontend address, and sets COOKIE_SECURE=false when that address is plain http on anything other than localhost.

Three things the file does not do:

  • No passwords or keys. The file is committed. DB_PASSWORD, JWT_SECRET and FAUXNANCE_API_KEY stay in .env on the box and in the trading-secrets Secret on EKS. apply.py leaves those lines alone.

Why the public IP needs four settings

Everything worked on the development box with no settings, then Register failed on EC2. The reason is the same for all four settings: the browser is now on a different machine from the containers.

Wrong address: AUTH_URL and BACKEND_URL

The frontend writes two addresses into every page it sends. Unset, they default to http://localhost:3000 and http://localhost:8085. In a browser, localhost means the laptop, where nothing is listening.

Closed ports: 3000 and 8085

Only :4200 is typed in the address bar, but the frontend container is not a middleman. The JavaScript in the browser calls the auth service and the trade API directly, so each needs its own inbound rule.

CORS: CORS_ALLOWED_ORIGINS

A page from port 4200 calling port 8085 is "cross-origin". The service being called decides which page addresses it accepts, so this is a backend setting. The auth service already accepts any page address. The trade API had localhost:4200 fixed in its code; it now reads the list from this setting. The value is the address of the page, not of the API.

Cookie: COOKIE_SECURE=false

Login issues a 15-minute access token and a long-lived refresh cookie. Browsers store a cookie marked Secure only over https, with an exception for localhost. Over http://<public-ip> the cookie is dropped and the session ends when the token expires.

Cost of the flag. With it off, the refresh cookie crosses the internet unencrypted. That is acceptable for a short-lived test box with test accounts, not for real users. The proper fix is https, which the EKS setup provides.

Nothing changed inside the Docker network. Containers still reach each other by service name (postgres, kafka:29092). Only the addresses handed to the browser changed.

Session Manager and EKS are two separate things. Session Manager only gives you a terminal on the EC2 box. kubectl is a program on that box that sends requests over the network to the cluster's API server, and the cluster decides for itself whether to accept them.

The cluster asks two questions on every request:

Add the disk add-on

Runs in: EC2 box, in the session

A pod's own storage is temporary: when the pod restarts, everything it wrote is gone. Kafka holds messages that must survive a restart, so it needs a real disk that lives outside the pod. On AWS that disk is an EBS volume.

The idea: a claim and something to answer it

A pod cannot create an EBS volume itself. It can only file a request, called a claim: "I need 2 GB of type gp3". Something in the cluster has to notice that claim, ask AWS to create the volume, attach it to the node the pod runs on, and hand it to the pod. That something is the EBS CSI driver, and on EKS it is installed as an add-on.

The cluster did not have it: aws eks list-addons showed only coredns, kube-proxy, metrics-server and vpc-cni. The gp2 storage class that was listed does not work on Kubernetes 1.34 without the driver.

Without the add-on the damage spreads. Kafka never starts. The order service and the executor each wait for Kafka's topics before starting, so they never start either. Only the frontend and auth service would come up: the page would load and login would work, but nothing to do with orders.

Why a policy is attached to the node role

Creating and attaching a volume are calls to AWS, and AWS only accepts calls from an identity that is allowed to make them. The add-on runs on the worker nodes and uses the nodes' IAM role. AmazonEBSCSIDriverPolicy gives that role permission to create, attach and delete EBS volumes. Without it the add-on would be installed but every disk request would be refused by AWS.

The idea: two networks and one firewall

A VPC is a private network inside AWS. Machines in the same VPC can talk to each other on private addresses. Machines in different VPCs cannot, unless something joins the two.

This setup has two VPCs. The EC2 box and the database are in the account's default VPC (172.31.0.0/16). eksctl created a brand new VPC for the cluster (192.168.0.0/16). So the box could reach the database from the start, and the pods could not.

A security group is the firewall on a single resource. The database's security group lists which addresses may connect to port 5432. Being on a connected network is not enough; the address must also be on that list.

VPC peering is a private link between two VPCs. With it, and a route on each side saying "traffic for the other network goes through the link", machines in one VPC reach machines in the other on private addresses, without touching the internet.

Why peering, not a public database

Both were tried. The database was first made public (see Test the application against RDS before containers) with one security group rule per node. That worked, but it has a flaw: each rule names one node's public IP, and a node that is replaced or added gets a new IP that is not on the list. It was then replaced by peering.

The load balancers

The line type: LoadBalancer in a Service file is what makes AWS build a load balancer. Nothing is created in the AWS console by hand. Each gets its own public hostname and forwards one port to one pod.

# k8s-tester/frontend-service.yaml
spec:
  type: LoadBalancer        # this line makes AWS create a load balancer
  selector:
    app: frontend           # send traffic to pods labelled app=frontend
  ports:
    - port: 4200            # port the load balancer listens on
      targetPort: http      # the pod's port named "http" (4200)

Kafka's Service has no type: LoadBalancer, so Kafka only gets an internal name. The executor's load balancer exists because one per service was asked for; the browser never calls it.

Known limit, since removed. This layout was replaced by a single load balancer; see One load balancer and an Ingress. Each load balancer has its own hostname. Over plain http the browser will not send the refresh cookie from the frontend's hostname to the auth service's hostname, so a login lasts until the 15-minute access token expires. One shared entry point with https removes this.

How the addresses changed without changing code

The same images run on the development box, on the EC2 box and on EKS, each with different addresses, and no code was edited between them. That works because an address is not written into the code. The code asks its environment for it when the program starts.

The chain, for the frontend's AUTH_URL

  1. The code reads a variable, with a fallback. In sprint8/front-end/app.py:
    AUTH_URL = os.getenv('AUTH_URL', 'http://localhost:3000')
    If a variable named AUTH_URL exists it is used; otherwise localhost.
  2. The page is filled in from that value. The templates contain const AUTH_URL = "{{ AUTH_URL }}";, so every page sent to the browser carries whatever the variable held.
  3. Kubernetes sets the variable from the ConfigMap. frontend-deployment.yaml says envFrom: configMapRef: trading-config, which turns every ConfigMap entry into an environment variable when the pod starts.
  4. Changing the ConfigMap and restarting the pod changes the address. The image is untouched.

One load balancer and an Ingress

The four separate load balancers were replaced by one. A single Application Load Balancer (ALB) now receives every request, and an Ingress holds the rules that decide which service each request goes to. Switched on 4 October with k8s-ingress/enable-ingress.sh.

The three pieces

Ingress. A Kubernetes object that says how outside requests are routed by path. It is only a description. k8s-ingress/ingress.yaml:

PathGoes to
/auth/...auth-service:3000
/api/v1/...order-service:8085
anything elsefrontend:4200

The most specific path wins, so /auth/login goes to the auth service even though it also matches "anything else". The split works because the browser only ever calls /auth/... on the auth service and /api/v1/... on the trade API.

AWS Load Balancer Controller. A pod in the kube-system namespace that watches for Ingress objects and builds the matching load balancer in AWS. Without it, an Ingress is accepted by the cluster and then nothing happens. It is the same idea as the disk add-on: one object asks, another piece of software makes it real.

You writeWhat makes it real
A disk claimEBS CSI add-on
A Service with type: LoadBalancerBuilt into EKS
An IngressAWS Load Balancer Controller

Helm. A package installer for Kubernetes, as dnf is for Amazon Linux. The controller is not one file: it is about a dozen objects that must agree with each other, including a webhook with a certificate generated at install time. AWS publishes them as a Helm chart, and one command installs the lot with three values filled in. Helm is used only for the controller; the application is still applied with kubectl apply -k.

helm upgrade --install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName=capstone --set region=ap-south-1 --set vpcId=<cluster VPC>

Why the controller needs an IAM policy

Building a load balancer is a set of calls to AWS. The controller runs on the worker nodes and uses their IAM role, so that role is given a policy (AWSLoadBalancerControllerIAMPolicy, from the controller's own project) allowing it to create and manage load balancers, target groups and security group rules. This is the same pattern as the disk add-on's policy.

The application on EKS does not depend on Jenkins being up. Jenkins is needed only at the moment of deploying.

Image tags. Every build tags its images with the first 12 characters of the commit it was built from, for example trading-frontend:6e4dbe070fa7. The tag says exactly which code a pod is running, and rolling back is a matter of deploying an older tag.

Tests in containers. The two test stages run inside throwaway Maven and Node containers, so the box needs neither Java build tools nor Node installed.

The four application images should end in the commit ID of the build, and their pods should be minutes old. A tag of 1.0 means the hand-pushed images; a 12-character commit ID can only have come from Jenkins. In Jenkins, an automatic build opens with Started by GitHub push.

All four application pods restart on every build, even when one service changed, because all four images receive the new tag.

Why the second build is much faster

The first build starts from nothing. Later ones reuse its work: Maven dependencies stay in Jenkins's ~/.m2 folder, Docker skips every build step whose inputs did not change, and ECR skips uploading layers it already has. A one-file change to the frontend rebuilds one step of one image.

Building another branch

Build with Parameters takes a branch name. The job always follows main; when another branch is given, the pipeline's first stage switches the workspace to it. The branch must contain scripts/ and k8s-ingress/. There is one cluster and one namespace, so building a branch replaces what is running until main is built again.
