What was tested, 10 October 2026. On a Linux machine with Docker: every image built from these Dockerfiles; docker compose up brought Postgres, Kafka, the topics and all four applications up healthy; a browser signed in as demo and loaded the dashboard both with separate API ports (EC2 style) and with page and APIs on one address (Ingress/CloudFront style); an order was placed and its ORDER_PLACED event reached Kafka and the executor; load-db.sh and the whole stack ran against a Postgres that only accepts encrypted connections (standing in for RDS); the 465 frontend unit tests pass with the code change. CORS: list the addresses, do not use *. Both services send the login cookie (credentials), and browsers refuse Access-Control-Allow-Origin: * together with credentials; Spring even refuses to start with * and allowCredentials(true). CORS_ALLOWED_ORIGINS takes a comma-separated list of exact origins (scheme://host[:port], no trailing slash), so every stage is a setting, not a code change. With one ALB or CloudFront the page and the APIs share one address and CORS does not apply at all.

2. Code changes

2.1 Angular: read the API addresses at start, not at build (done in this kit)

An Angular build is static files: whatever address is compiled in is used everywhere the image runs. This project generated src/environments/*.ts from Config/application.yml at build time, so one image could only ever call localhost. Three edits make the addresses a runtime setting; npm start on a laptop behaves exactly as before.

Frontend/src/index.html, inside <head>, before the app:

<base href="/">
<!-- API addresses written when the container starts (see Dockerfile); must load before the app. -->
<script src="app-config.js"></script>

Frontend/public/app-config.js (new; the container overwrites it):

window.__APP_CONFIG__ = window.__APP_CONFIG__ || {};

Frontend/scripts/sync-config.mjs, the template it writes into src/environments/environment*.ts (both regenerated):

const runtime = (globalThis as { __APP_CONFIG__?: { tradeApiUrl?: string; authApiUrl?: string } }).__APP_CONFIG__ ?? {};
const pick = (value: string | undefined, fallback: string): string =>
  (typeof value === 'string' ? value : fallback).replace(/\/+$/, '');
const tradeApiUrl = pick(runtime.tradeApiUrl, 'http://localhost:8081');   // build-time default
const authApiUrl = pick(runtime.authApiUrl, 'http://localhost:3000');
/** The origin a URL points at; a relative or empty URL is the page's own origin. */
const originOf = (url: string): string => new URL(url || '/', globalThis.location?.origin).origin;
...
  platformOrigins: [originOf(tradeApiUrl), originOf(authApiUrl)],

Frontend/src/app/core/interceptors/auth.interceptor.ts: relative URLs (/api/v1/..., used when the address is empty) are resolved against the page, so they still get the bearer token:

const parsed = new URL(url, globalThis.location?.origin);
...
if (target.origin === new URL(environment.authApiUrl || '/', globalThis.location?.origin).origin) {

For another Angular project: find where the base URL lives (environment.ts, an API_URL constant, an HttpInterceptor), make it read window.__APP_CONFIG__.<key> first, add the <script> and public/app-config.js, then set RUNTIME_CONFIG to key:ENV_VAR pairs (default authApiUrl:AUTH_SERVICE_URL,tradeApiUrl:ORDER_SERVICE_URL). An empty value means "same address as the page", so services must be called with paths like ${base}/api/.... Angular versions before 17 keep static files in src/assets/ instead of public/: put app-config.js there and use <script src="assets/app-config.js">, and set RUNTIME_CONFIG's output path accordingly in the Dockerfile's script (the file it writes).

2.2 Backends: nothing to change in this project

Every address, port and secret is already read from environment variables with a fallback to Config/application.yml; CORS (CORS_ALLOWED_ORIGINS) and the cookie flag (COOKIE_SECURE) are settings. Things to check in other projects:

Look for If found
localhost or a fixed URL in Java/TS code Replace with ${SOME_URL:http://localhost:8081} (Spring) or process.env.SOME_URL ?? 'http://localhost:3000' (Node), then add the variable to config.env
CORS origins fixed in code (@CrossOrigin(origins="http://localhost:4200"), allowedOrigins("..."), enableCors({origin: '...'})) Read them from a variable, as this project does: cors.allowed-origins: ${CORS_ALLOWED_ORIGINS:http://localhost:4200}
allowedOrigins("*") with allowCredentials(true) Spring refuses to start. Use the variable, or allowedOriginPatterns("*") only for a throw-away demo
A refresh cookie with secure: true fixed Make it a setting: browsers drop Secure cookies over plain http (EC2 IP, ELB, ALB)
Node pg with no ssl option Set PGSSLMODE=no-verify for RDS (already in config.env); pg reads it
spring.datasource.url with localhost jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:...}
A jar name fixed in the old Dockerfile (here: sprint-06-trade-api-1.0-SNAPSHOT.jar) Nothing: the generic Dockerfile copies whichever jar Maven built
Frontend routes that start with /auth or /api Rename them, or change the Ingress/CloudFront prefixes: those paths go to the backends

3. The EC2 box

3.1 Launch it

AWS console, your region

  1. EC2 → Launch instance. Name deploy-box. AMI Amazon Linux 2023. Type t3.xlarge (4 vCPU, 16 GB). Storage 30 GB gp3.
  2. Key pair: none needed (Session Manager is used). Network: default VPC, a public subnet, auto-assign public IP on.
  3. Security group deploy-box-sg, inbound from My IP only: TCP 4200 (page), 3000 (auth), 8081 (order API). Nothing for 22, 5432, 9092 or 8082.
  4. Advanced details → IAM instance profile: a role with AmazonSSMManagedInstanceCore and, because eksctl creates VPCs, IAM roles and CloudFormation stacks, AdministratorAccess (your own sandbox account only). The box then needs no access keys; never put keys in a file or in git.
  5. Launch, then Connect → Session Manager → Connect, and sudo su - ec2-user.

Optional: allocate an Elastic IP and associate it, so the IP in .env survives a stop/start.

5. RDS

5.1 Create the database

EC2 box

REGION=$(aws configure get region || curl -s http://169.254.169.254/latest/meta-data/placement/region)
VPC=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query 'Vpcs[0].VpcId' --output text)
BOX_SG=$(aws ec2 describe-security-groups --filters Name=group-name,Values=deploy-box-sg --query 'SecurityGroups[0].GroupId' --output text)

RDS_SG=$(aws ec2 create-security-group --group-name trading-rds-sg --description "Postgres for the trading app" \
  --vpc-id $VPC --query GroupId --output text)
# the box may connect (same VPC)
aws ec2 authorize-security-group-ingress --group-id $RDS_SG --protocol tcp --port 5432 --source-group $BOX_SG

read -s -p "RDS master password: " PGPASSWORD; export PGPASSWORD; echo
aws rds create-db-instance --db-instance-identifier trading-db \
  --engine postgres --db-instance-class db.t4g.micro --allocated-storage 20 --storage-type gp3 \
  --master-username postgres --master-user-password "$PGPASSWORD" \
  --vpc-security-group-ids $RDS_SG --publicly-accessible --backup-retention-period 0 --no-multi-az \
  --query 'DBInstance.DBInstanceStatus' --output text
aws rds wait db-instance-available --db-instance-identifier trading-db       # 5-10 silent minutes
RDS=$(aws rds describe-db-instances --db-instance-identifier trading-db --query 'DBInstances[0].Endpoint.Address' --output text)
echo $RDS

"Publicly accessible" gives it a public name; the security group still decides who may connect. Never open 5432 to 0.0.0.0/0.

7.2 Let the cluster reach RDS: VPC peering

RDS is in the default VPC (172.31.0.0/16), the pods in the cluster's VPC. Peering joins them privately; one security group rule then covers every node, including replaced ones.

EKS_VPC=$(aws eks describe-cluster --name capstone --query 'cluster.resourcesVpcConfig.vpcId' --output text)
EKS_CIDR=$(aws ec2 describe-vpcs --vpc-ids $EKS_VPC --query 'Vpcs[0].CidrBlock' --output text)
RDS_CIDR=$(aws ec2 describe-vpcs --vpc-ids $VPC --query 'Vpcs[0].CidrBlock' --output text)
echo "cluster $EKS_CIDR  database $RDS_CIDR"     # must not overlap

PCX=$(aws ec2 create-vpc-peering-connection --vpc-id $EKS_VPC --peer-vpc-id $VPC \
  --query 'VpcPeeringConnection.VpcPeeringConnectionId' --output text)
aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id $PCX --query 'VpcPeeringConnection.Status.Code' --output text
sleep 5
# the RDS name resolves to its PRIVATE address from the cluster, so traffic uses the link
aws ec2 modify-vpc-peering-connection-options --vpc-peering-connection-id $PCX \
  --requester-peering-connection-options AllowDnsResolutionFromRemoteVpc=true \
  --accepter-peering-connection-options AllowDnsResolutionFromRemoteVpc=true

for rt in $(aws ec2 describe-route-tables --filters Name=vpc-id,Values=$EKS_VPC --query 'RouteTables[].RouteTableId' --output text); do
  aws ec2 create-route --route-table-id $rt --destination-cidr-block $RDS_CIDR --vpc-peering-connection-id $PCX >/dev/null; done
for rt in $(aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC --query 'RouteTables[].RouteTableId' --output text); do
  aws ec2 create-route --route-table-id $rt --destination-cidr-block $EKS_CIDR --vpc-peering-connection-id $PCX >/dev/null; done
aws ec2 authorize-security-group-ingress --group-id $RDS_SG --protocol tcp --port 5432 --cidr $EKS_CIDR

# test from a pod
kubectl run pgtest --restart=Never --image=postgres:16-alpine -- pg_isready -h $RDS -p 5432 -t 10
sleep 20; kubectl logs pgtest; kubectl delete pod pgtest

8.3 Give the browser the load balancer addresses

deploy/set-urls.sh

It waits for the hostnames, writes k8s/overlays/1-four-elb/urls.env (auth and order addresses for the browser, the frontend's address for CORS) and applies it. Open the printed address (give a new load balancer 2-3 minutes). Commit urls.env if you want the pipeline to keep it.

Known limit of this approach. The page and the two APIs have three different hostnames, so the browser treats the auth service as another site and does not send the refresh cookie back: signing in works, but the session ends when the 15-minute access token expires. One address (approach 2) fixes it. The executor's load balancer exists because each service got one; nothing calls it.

9. Kubernetes, approach 2: one ALB and an Ingress

deploy/install-lb-controller.sh capstone $REGION     # once per cluster
kubectl apply -k k8s/overlays/2-ingress
deploy/set-urls.sh ingress
kubectl -n trading get ingress,svc

The Services go back to ClusterIP (AWS deletes the four ELBs), and the controller builds one ALB from base/ingress.yaml: /auth → auth-service, /api → order-service, everything else → frontend. The browser addresses are empty, so the page calls its own address. Test: open http://<ALB address>, sign in, then

ALB=$(kubectl -n trading get ingress app -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -s http://$ALB/app-config.js; curl -s -o /dev/null -w '%{http_code}\n' http://$ALB/api/v1/accounts/1   # 401 without a token

If the address stays empty: kubectl -n trading describe ingress app and kubectl -n kube-system logs deploy/aws-load-balancer-controller.

10. Approach 3: frontend on S3, CloudFront in front

Serving static files from S3 through CloudFront is better than an nginx pod: no pod to run, files cached at the edge near the user, and https for free. The ALB keeps serving the APIs; CloudFront sends /auth/* and /api/* to it, so page and APIs still share one address.

BUCKET=trading-frontend-$ACCOUNT                  # bucket names are global
aws s3 mb s3://$BUCKET --region $REGION           # stays private: Block Public Access is on by default

deploy/publish-frontend.sh $BUCKET                # files from the tested frontend image, app-config.js = same address
kubectl apply -k k8s/overlays/3-cloudfront        # Ingress keeps /auth and /api only
kubectl -n trading delete deployment frontend service frontend --ignore-not-found
deploy/cloudfront.sh $BUCKET                      # prints the distribution id and https://dxxxx.cloudfront.net
aws cloudfront wait distribution-deployed --id <DIST_ID>

What cloudfront.sh creates: an Origin Access Control (the bucket is read only by CloudFront, signed), a CloudFront Function that answers app routes like /dashboard with index.html, the distribution from deploy/cloudfront-distribution.json (S3 origin cached with CachingOptimized; ALB origin for /api/* and /auth/* over http with no caching and all headers, cookies and query strings forwarded, so Authorization and the refresh cookie reach the services), and the bucket policy.

Then tell the services the new https address and turn on Secure cookies:

vi k8s/overlays/3-cloudfront/urls.env     # CORS_ALLOWED_ORIGINS=https://dxxxx.cloudfront.net   FRONTEND_URL=same   COOKIE_SECURE=true
kubectl apply -k k8s/overlays/3-cloudfront

Open https://dxxxx.cloudfront.net and sign in. After a frontend change: rebuild and push the image, then DIST_ID=<id> deploy/publish-frontend.sh $BUCKET (it uploads and clears index.html and app-config.js from the cache).

11. Your domain: Route 53 and ACM

Needs a public hosted zone in Route 53 in this account for your domain (Route 53 → Registered domains to buy one, or delegate a subdomain such as team3.example.com from whoever owns example.com by adding the zone's four NS records there).

deploy/domain.sh <DIST_ID> trade.example.com

It requests an ACM certificate in us-east-1 (CloudFront only reads certificates there), adds the validation CNAME to your zone and waits until it is issued, adds the name and certificate to the distribution, and creates an alias A record from the name to CloudFront. Then:

vi k8s/overlays/3-cloudfront/urls.env     # CORS_ALLOWED_ORIGINS=https://trade.example.com,https://dxxxx.cloudfront.net  FRONTEND_URL=https://trade.example.com
kubectl apply -k k8s/overlays/3-cloudfront
aws cloudfront wait distribution-deployed --id <DIST_ID>
curl -sI https://trade.example.com | head -1

Open https://trade.example.com. That is the final address.
