  10. STAGE 9PolishPLANNED

Localhost, service names, and CORS

IN PLAIN WORDSAn address only makes sense from where you are standing. localhost means "this same machine". Inside a container, "this machine" is the container itself, not your laptop and not the database next door.

Three rules

1 · Server to server: use the name

Docker gives every Compose service a name on its private network: postgres, kafka. Kubernetes does the same with Services: demo-kafka. The name always finds the right container, even if its IP changes.

2 · Browser to server: use the public door

The browser is on your computer, outside Docker. It has never heard of postgres or trade-api. It can only use localhost:PORT (Compose publishes the port) or the public domain (EKS).

3 · Change settings, not code

The code says "use DB_HOST, or localhost if not set". Compose and Helm set DB_HOST for us. Same image everywhere; only the environment variables change.

Why not just keep localhost?

Run on your laptop with no Docker, everything really is on one machine, so localhost:5432 works. Put each service in its own container and each one becomes its own tiny machine. Now localhost:5432 inside the trade API means "port 5432 inside the trade API container". Nothing is listening there, so the connection fails.

The one that trips people up: BACKEND_URL and AUTH_URL are set on the frontend container, but Flask writes them into the HTML page and the browser uses them. So they must be addresses the browser can reach. http://trade-api:8085 would be wrong here even though it works between containers. Compose leaves them at localhost; the Helm chart sets them to https://demo.apps.example.com.

Kafka shows the same idea in one container: it listens on kafka:29092 for other containers and on localhost:9092 for tools on the host. And if you open the page from a different computer than the one running Docker, localhost is your computer, not the Docker host; use the host's address or an SSH tunnel.

CORS in one minute

IN PLAIN WORDSAn origin is scheme + host + port. A web page may freely call its own origin. To call any other origin, the browser first asks that server, "do you allow pages from over there?" CORS is the server's answer. It is a browser safety rule only. Server-to-server calls never involve CORS.

Compose: CORS is needed

The page comes from http://localhost:4200. It calls :3000 and :8085. Different port means different origin, so both APIs must say "localhost:4200 is allowed".

EKS: CORS goes away

Page, auth, and trade API all live under https://demo.apps.example.com. The load balancer splits them by path. Same origin, so the browser never asks. This is the reason we use one hostname with paths.

Where the CORS settings live, and when to change them

FileWhat it does todayChange it when
sprint8/.../config/WebConfig.java:13Trade API allows only localhost:4200, 127.0.0.1:4200, and frontend:4200. The list is fixed in code.You put the API on a different hostname than the page (for example api.example.com). Then add the page's public origin, ideally from an env var. The frontend:4200 entry never helps: no browser ever sees that name.
sprint8/.../JwtAuthenticationFilter.java:65On a 401 it always answers "allowed origin: http://localhost:4200".Same case as above. On one shared hostname it is harmless.
sprint8-auth-service/src/init-app.ts:20Auth service allows any origin, with cookies.Before production. It works everywhere, but it is too open; limit it to your real origin.
Chart env COOKIE_SAMESITE=lax, COOKIE_SECURE=trueThe login cookie is sent only over HTTPS and only to the same site.Only if page and API move to different sites. Then the cookie needs SameSite=None.
One thing to watch on EKS: the browser speaks HTTPS, but the load balancer talks plain HTTP to the pod. If the trade API ever answers 403 Invalid CORS request when you place an order, Spring has mistaken that for a cross-origin call. Spring Boot normally reads the load balancer's forwarded headers on Kubernetes and gets it right. If not, set the env var SERVER_FORWARD_HEADERS_STRATEGY=native on the order service, or add the public origin to WebConfig.java.

05

Move images to ECR

IN PLAIN WORDSECR is AWS's own image shelf. Because it lives in the same account as the cluster, the nodes can pull images using their built-in AWS identity. No registry password is needed inside the cluster.

1 · CREATE FOUR REPOSITORIES
AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
ECR_REGISTRY="$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com"
for repo in trading-frontend trading-auth-service trading-trade-api trading-executor; do
  aws ecr describe-repositories --region "$AWS_REGION" --repository-names "$repo" >/dev/null 2>&1 || \
  aws ecr create-repository --region "$AWS_REGION" --repository-name "$repo" \
    --image-tag-mutability IMMUTABLE --image-scanning-configuration scanOnPush=true
done
2 · LOG IN, RETAG, PUSH
aws ecr get-login-password --region "$AWS_REGION" \
  | docker login --username AWS --password-stdin "$ECR_REGISTRY"
for image in trading-frontend trading-auth-service trading-trade-api trading-executor; do
  docker tag "$image:1.0" "$ECR_REGISTRY/$image:1.0" || exit $?
  docker push "$ECR_REGISTRY/$image:1.0" || exit $?
done

Immutable means a tag can never be overwritten. A rebuilt image needs a new tag, such as 1.0.1. That way 1.0 always means exactly one thing.

06

Create the RDS database

IN PLAIN WORDSContainers come and go, so data must not live inside them. RDS is PostgreSQL run by AWS. We put it in the cluster's private network and add a firewall rule: only the cluster's servers may connect.

1 · FIND THE CLUSTER NETWORK, ADD THE FIREWALL RULE
VPC_ID=$(aws eks describe-cluster --name trading-platform --region "$AWS_REGION" \
  --query 'cluster.resourcesVpcConfig.vpcId' --output text)
CLUSTER_SG=$(aws eks describe-cluster --name trading-platform --region "$AWS_REGION" \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId' --output text)
# List the private subnets. Note two IDs in different zones.
aws ec2 describe-subnets --region "$AWS_REGION" \
  --filters "Name=vpc-id,Values=$VPC_ID" "Name=tag:kubernetes.io/role/internal-elb,Values=1" \
  --query 'Subnets[].[SubnetId,AvailabilityZone]' --output table
RDS_SG=$(aws ec2 create-security-group --region "$AWS_REGION" --vpc-id "$VPC_ID" \
  --group-name trading-rds --description 'Postgres from EKS nodes only' \
  --query GroupId --output text)
aws ec2 authorize-security-group-ingress --region "$AWS_REGION" --group-id "$RDS_SG" \
  --protocol tcp --port 5432 --source-group "$CLUSTER_SG"
2 · CREATE THE DATABASE SERVER
aws rds create-db-subnet-group --region "$AWS_REGION" \
  --db-subnet-group-name trading-private-db \
  --db-subnet-group-description 'Private trading DB subnets' \
  --subnet-ids <private-subnet-a> <private-subnet-b>
aws rds create-db-instance --region "$AWS_REGION" \
  --db-instance-identifier trading-db --engine postgres \
  --db-instance-class db.t4g.micro --allocated-storage 20 --storage-type gp3 \
  --storage-encrypted --db-subnet-group-name trading-private-db \
  --vpc-security-group-ids "$RDS_SG" \
  --master-username dbadmin --manage-master-user-password \
  --backup-retention-period 7 --no-publicly-accessible
aws rds wait db-instance-available --region "$AWS_REGION" --db-instance-identifier trading-db
aws rds describe-db-instances --region "$AWS_REGION" --db-instance-identifier trading-db \
  --query 'DBInstances[0].Endpoint.Address' --output text      # this is <rds-endpoint>

AWS creates the dbadmin password and stores it in Secrets Manager. Look it up there when psql asks.

Load the tables

The database is private, so your terminal cannot reach it. We start a small helper pod inside the cluster and run psql from there.

3 · START A HELPER POD AND COPY THE SQL IN
# The repo schema has one line for a user named "postgres". RDS has no such user, so drop it.
sed '/^ALTER ROLE postgres IN DATABASE/d' sprint8/db/schema.sql > /tmp/schema-rds.sql

kubectl -n trading run psql-client --image=postgres:16-alpine --restart=Never --command -- sleep 3600
kubectl -n trading wait --for=condition=Ready pod/psql-client --timeout=120s
kubectl -n trading cp /tmp/schema-rds.sql psql-client:/tmp/schema-rds.sql
kubectl -n trading cp sprint8/db/seed-data.sql psql-client:/tmp/seed-data.sql
kubectl -n trading exec -it psql-client -- sh
4 · INSIDE THE POD: MAKE THE APP USER AND DATABASE
psql -W "host=<rds-endpoint> port=5432 dbname=postgres user=dbadmin sslmode=require"

CREATE ROLE trading_app LOGIN;
\password trading_app
GRANT trading_app TO CURRENT_USER;
CREATE DATABASE trading_system_db OWNER trading_app;
\q
5 · INSIDE THE POD: TABLES, SAMPLE DATA, PERMISSIONS
DB="host=<rds-endpoint> port=5432 dbname=trading_system_db user=dbadmin sslmode=require"
psql -W "$DB" -f /tmp/schema-rds.sql
psql -W "$DB" -f /tmp/seed-data.sql
psql -W "$DB" <<'SQL'
GRANT USAGE, CREATE ON SCHEMA auth, trading TO trading_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA auth, trading TO trading_app;
GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES IN SCHEMA auth, trading TO trading_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA auth, trading
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO trading_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA auth, trading
  GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO trading_app;
ALTER ROLE trading_app IN DATABASE trading_system_db SET search_path TO trading, public;
SQL
exit
6 · REMOVE THE HELPER POD
kubectl -n trading delete pod psql-client

Two users on purpose: dbadmin owns the tables and is for humans; trading_app can only read and write rows and is what the app uses. If the app's password leaks, nobody can drop tables with it.

IN PLAIN WORDSThe app needs three secret values. We keep them in one AWS safe (Secrets Manager). A small helper in the cluster, External Secrets, is given a key to that one safe and keeps a copy fresh for the pods. Nothing secret is ever typed into Git, Helm, or Jenkins.

09

Get the HTTPS certificates

IN PLAIN WORDSA certificate is what puts the padlock in the browser. AWS gives them free, but first you must prove you own the domain by adding one record to its DNS zone. We need two copies: one for the load balancer and one for CloudFront.

Certificate forMust be in regionUsed in
Load balancer (ALB)Your cluster regionStep 10
CloudFrontAlways us-east-1Step 11

You need the domain's hosted zone in Route 53 already. This step only adds a small proof record to it. The record that sends users to the site comes last, in step 12.

REQUEST BOTH, PROVE OWNERSHIP, WAIT
CERT_ARN=$(aws acm request-certificate --region "$AWS_REGION" \
  --domain-name 'demo.apps.example.com' --validation-method DNS \
  --query CertificateArn --output text)
CF_CERT_ARN=$(aws acm request-certificate --region us-east-1 \
  --domain-name 'demo.apps.example.com' --validation-method DNS \
  --query CertificateArn --output text)

# Show the proof record. Add it to the hosted zone as a CNAME.
aws acm describe-certificate --region "$AWS_REGION" --certificate-arn "$CERT_ARN" \
  --query 'Certificate.DomainValidationOptions[0].ResourceRecord'
aws acm describe-certificate --region us-east-1 --certificate-arn "$CF_CERT_ARN" \
  --query 'Certificate.DomainValidationOptions[0].ResourceRecord'

aws acm wait certificate-validated --region "$AWS_REGION" --certificate-arn "$CERT_ARN"
aws acm wait certificate-validated --region us-east-1 --certificate-arn "$CF_CERT_ARN"

Both requests usually show the same proof record, so one CNAME covers both. If your cluster region is already us-east-1, one certificate serves both jobs.

Do not add --wait. Two pods wait for Kafka topics, and the topics are made by a job that Helm starts only after the install returns. With --wait each side waits for the other and the install times out.
WATCH IT COME UP
kubectl -n trading get pods -w             # all five should reach Running, 1/1
kubectl -n trading get ingress demo-trading   # ADDRESS shows the load balancer name
kubectl -n trading get events --sort-by=.lastTimestamp | tail -20

Test it before any DNS exists: curl -k -H 'Host: demo.apps.example.com' https://<alb-address>/auth/public-key

11

Put CloudFront in front

IN PLAIN WORDSCloudFront is AWS's global front desk. Users connect to a CloudFront location near them, and CloudFront passes the request to our load balancer. For now it forwards everything, unchanged. Later it can also serve static files from S3 without the address changing.

Why before DNS?

DNS should point at the final front door. If we pointed it at the load balancer now, we would have to change it again later. Build CloudFront first, point DNS once.

What users gain

HTTPS at the edge, protection from traffic floods, and room to add caching and a firewall (WAF) later.

What does not change

Still one hostname, still routed by path. So it is still one origin and CORS stays out of the picture.

Create the distribution

The console is easiest: CloudFront → Create distribution. Use these settings.

SettingValueWhy
Origin domainThe ALB address from step 10Where CloudFront sends requests.
Origin protocolHTTPS onlyKeep the hop to the load balancer encrypted.
Viewer protocolRedirect HTTP to HTTPSNobody uses plain HTTP.
Allowed methodsGET, HEAD, OPTIONS, PUT, POST, PATCH, DELETELogin and orders are POST requests.
Cache policyCachingDisabledPages and API answers differ per user. Never cache them.
Origin request policyAllViewerPasses cookies, the login token, and the Host name through.
Alternate domain namedemo.apps.example.comThe name users will type.
Certificate$CF_CERT_ARN (us-east-1)The padlock for that name.
Why AllViewer matters: the load balancer only answers requests for the host demo.apps.example.com. If CloudFront did not pass the Host name along, the load balancer would return 404.
FIND THE CLOUDFRONT ADDRESS
aws cloudfront list-distributions \
  --query "DistributionList.Items[?Aliases.Items[0]=='demo.apps.example.com'].[Id,DomainName,Status]" \
  --output table
# When Status is Deployed, the DomainName looks like d1234abcd.cloudfront.net

Later: static files from S3

Today the frontend is a Flask app that builds pages and also serves the analytics API, so it cannot simply be copied to S3. When it is split into plain static files, add S3 as a second origin for those files and keep /auth and /api/v1 going to the load balancer. Users notice nothing; the address stays the same.

Optional lock-down: limit the load balancer so it accepts traffic only from CloudFront (AWS publishes a managed prefix list for this). Then nobody can skip the front desk.

12

Point the domain with Route 53

IN PLAIN WORDSDNS is the internet's phone book. This last step adds one entry: "demo.apps.example.com lives at this CloudFront address." After that, the name works for everyone.

ONE ALIAS RECORD → CLOUDFRONT
cat > /tmp/alias.json <<'EOF'
{ "Changes": [{ "Action": "UPSERT", "ResourceRecordSet": {
    "Name": "demo.apps.example.com", "Type": "A",
    "AliasTarget": { "HostedZoneId": "Z2FDTNDATAQYW2",
                     "DNSName": "<dXXXX.cloudfront.net>",
                     "EvaluateTargetHealth": false } } }] }
EOF
aws route53 change-resource-record-sets --hosted-zone-id '<your-hosted-zone-id>' \
  --change-batch file:///tmp/alias.json

curl -sI https://demo.apps.example.com/ | head -5

Z2FDTNDATAQYW2 is a fixed ID that means "CloudFront" in every alias record; it is not your zone. Add a second record with "Type": "AAAA" for IPv6.

GitOps with Argo CD

IN PLAIN WORDSInstead of a person running helm, we write down what should be running in a Git repo. Argo CD lives in the cluster, reads that repo, and makes the cluster match. To deploy, you change a file. To undo, you revert it.

App repo

Source code, tests, Dockerfiles. "How to build it."

GitOps repo

The chart and a values file with the image tag. "What should be running." No secrets.

GITOPS REPO LAYOUT
trading-platform-gitops/

Jenkins builds the images

IN PLAIN WORDSJenkins is the factory. On every code change it runs the tests, builds the four images, pushes them to ECR, and opens a pull request that says "please run this new tag". It never logs in to the cluster; Argo CD does the delivery.

WhatWhere it lives
Region, registry address, image namesIn the Jenkinsfile. Not secret.
AWS accessThe build machine's own AWS role. No stored keys.
Permission to open the GitOps PRJenkins Credentials (a bot or GitHub App).
DB password, JWT secret, API keySecrets Manager only. Jenkins never sees them.
INSTALL ON A PRIVATE UBUNTU SERVER
sudo apt update && sudo apt install -y fontconfig openjdk-21-jre wget
sudo install -d -m 0755 /etc/apt/keyrings
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" \
  | sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt update && sudo apt install -y jenkins
sudo systemctl enable --now jenkins

Jenkins changes its signing key from time to time. Confirm the key file name on the Jenkins install page first. Keep port 8080 private; never open it to the internet.

JENKINSFILE STARTER
pipeline {
  agent { label 'docker-build-agent' }
  options { timestamps(); disableConcurrentBuilds() }
  environment {
    AWS_REGION = '<chosen-region>'
    AWS_ACCOUNT_ID = '<target-account-id>'
    ECR_REGISTRY = "${AWS_ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"
    IMAGE_TAG = "${GIT_COMMIT.take(12)}"
  }
  stages {
    stage('Test') {
      // Replace with the real tests: mvn test, npm test
      steps { sh 'echo "Add tests before publishing" >&2; exit 1' }
    }
    stage('Build and push') {
      steps {
        sh '''#!/usr/bin/env bash
          set -euo pipefail
          aws ecr get-login-password --region "$AWS_REGION" \\
            | docker login --username AWS --password-stdin "$ECR_REGISTRY"
          docker build -t "$ECR_REGISTRY/trading-frontend:$IMAGE_TAG" -f sprint8/front-end/Dockerfile sprint8/front-end
          docker build -t "$ECR_REGISTRY/trading-auth-service:$IMAGE_TAG" -f sprint8-auth-service/Dockerfile sprint8-auth-service
          docker build -t "$ECR_REGISTRY/trading-trade-api:$IMAGE_TAG" -f sprint8/Dockerfile sprint8
          docker build -t "$ECR_REGISTRY/trading-executor:$IMAGE_TAG" -f executor/Dockerfile executor
          for image in trading-frontend trading-auth-service trading-trade-api trading-executor; do
            docker push "$ECR_REGISTRY/$image:$IMAGE_TAG"
          done
        '''
      }
    }
    stage('Propose release') {
      steps { echo 'Open a GitOps PR that sets image.tag to IMAGE_TAG.' }
    }
  }
}

The image tag is the Git commit ID, so every image traces back to the exact code that built it.
