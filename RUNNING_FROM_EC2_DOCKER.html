The short answer

Register failed because the page told your browser to call http://localhost:3000, and inside a browser localhost means your own laptop, not the EC2 box.

The page was opened from http://13.201.4.242:4200, so the page itself loaded fine. The Register button then tried to reach the auth service on the laptop, where nothing is running. Chrome also refuses that kind of call outright, which is this message:

Access to fetch at 'http://localhost:3000/auth/register' from origin 'http://13.201.4.242:4200'
has been blocked by CORS policy: The request client is not a secure context and the
resource is in more-private address space `loopback`.

The fix has three parts, each explained with a picture below:

  1. Tell the page the real address of the auth service and the trade API (the EC2 public IP, not localhost).
  2. Let the browser reach those two services: open ports 3000 and 8085, and let the trade API accept calls from the new page address (CORS).
  3. Let the login cookie survive on a plain http:// address (COOKIE_SECURE=false).

Who is who

There are three places, and most of the confusion comes from mixing them up.

The browser runs on your laptop. The EC2 box has a firewall (the security group) with one gate per port. Behind each gate sits one Docker container. The frontend container only hands out HTML pages; it does not talk to the other services for you.

Step 1: what happened when you clicked Register

The page came from the EC2 public IP, but the code inside it called localhost.

Why it had localhost in it. The frontend (sprint8/front-end/app.py) reads two settings, AUTH_URL and BACKEND_URL, and writes them into every page it sends. Nobody set them on the EC2 box, so they fell back to the defaults http://localhost:3000 and http://localhost:8085.

Why it works on a developer machine. When everything runs on one machine, the browser and the containers share the same localhost, so the default is correct by accident.

Fix 1. Set AUTH_URL=http://13.201.4.242:3000 and BACKEND_URL=http://13.201.4.242:8085, so the page hands the browser an address it can actually reach.

Step 2: why open 3000 and 8085 when you only type 4200

You type only :4200, but your browser quietly makes two more connections of its own, to :3000 and :8085.

The frontend container is not a middleman. It sends the page and its job is done. When you click Register or place an order, the JavaScript running in your browser calls the auth service and the trade API directly, across the internet, from your laptop.

A security group checks every incoming connection by port. A call to 13.201.4.242:3000 is a new connection to a different port, so the rule for 4200 does not cover it.

If 3000 or 8085 is not open, the browser shows a timeout instead of the CORS message.

Could we avoid opening them? Yes, by putting one reverse proxy in front so everything goes through a single port. That is what the EKS Helm chart in k8s/associate-stack does with its load balancer. For docker-compose on one box it is extra setup, so this fix opens the two ports instead.

Step 3: CORS, and why the change is on the backend

The CORS change goes on the backend, specifically the trade API, because the service being called is the one that decides who may call it.

What CORS is. A page loaded from one address (http://13.201.4.242:4200) calling a different address (http://13.201.4.242:8085) counts as "cross-origin", because the port differs. The browser tells the server which page is asking. The server answers with the page addresses it accepts. If the page is not on that list, the browser hides the answer from the page.

The frontend cannot grant itself permission; that would defeat the point. Only the server's list matters.

ServiceIts allow list beforeChange needed
auth-service (3000)accepts any page address (origin: true in init-app.ts)none
trade-api (8085)only localhost:4200, 127.0.0.1:4200, frontend:4200, written into WebConfig.javalist now read from CORS_ALLOWED_ORIGINS

One point about the error text: it says "CORS policy", but that particular message is Chrome refusing a public page calling localhost. It was the wrong-address problem from Step 1. The real CORS refusal would have shown up next, the first time the page called the trade API.

Fix 2. Set CORS_ALLOWED_ORIGINS=http://13.201.4.242:4200 on the box. The value is the address of the page, not of the API.

Step 4: why COOKIE_SECURE=false

COOKIE_SECURE=false is needed only because the box is reached over plain http://; without it you would be logged out after the access token expires.

How login stays alive. Login gives the browser two things: a short-lived access token (15 minutes by default, JWT_TTL_SECONDS=900) and a long-lived refresh_token cookie. When the access token expires, the page calls /auth/refresh, the browser attaches the cookie, and a new token comes back. You never notice.

A cookie marked Secure is only stored and sent over https://. Browsers make one exception, for localhost, which is why this never showed up on a developer machine. http://13.201.4.242 is neither, so the browser silently drops the cookie and the refresh call has nothing to send.

The cost. With the flag off, the refresh cookie crosses the internet unencrypted, so anyone on the network path could copy it and stay logged in as you. That is acceptable for a short-lived test box with test accounts. It is not acceptable for real users.

The proper fix later. Serve the site over https:// and set the flag back to true. The EKS setup already does this through the load balancer certificate.

This one is a setting only. No code changed for it: the auth service already read COOKIE_SECURE from the environment.

What to do on the EC2 box

  1. Pull this branch on the box: git fetch && git checkout docker-changes
  2. Add these four lines to .env on the box: 
    AUTH_URL=http://13.201.4.242:3000
BACKEND_URL=http://13.201.4.242:8085
CORS_ALLOWED_ORIGINS=http://13.201.4.242:4200
COOKIE_SECURE=false
  3. In the AWS console, add inbound rules for TCP 3000 and 8085 to the box's security group. Limiting the source to your own IP is safer than opening them to everyone.
  4. Rebuild and restart: docker-compose up --build -d
  5. Open http://13.201.4.242:4200, register, log in, and place an order.

Things to know:

  • If the box has no Elastic IP, its public IP changes on every stop and start, and the three address lines must be updated each time.
  • No changes at all are needed if you use a tunnel and browse http://localhost:4200 instead. flow.md section 6 has the SSH command; with SSM, a port-forwarding session does the same job.
  • For anything beyond testing, use https and set COOKIE_SECURE back to true.
