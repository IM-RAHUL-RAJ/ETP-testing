00A

Why EC2 public IP failed, and localhost worked

VS Code Remote SSH leaves Docker running on EC2 and can tunnel selected remote ports to your computer.

Direct public IP

The EC2 security group may block inbound ports. Even if 4200 loads, browser JavaScript calls localhost:3000 and localhost:8085; outside EC2, localhost means the visitor's own computer. The public-IP origin also fails this app's localhost CORS allowlist, and its Secure refresh cookie is not suitable for plain HTTP public-IP access.

VS Code SSH forwarding

Forwarded local ports travel through the SSH connection to the matching EC2 ports. Browser URLs remain localhost, so the browser API URLs, CORS allowlist, and local cookie behavior line up.

  1. Connect to EC2 with VS Code Remote-SSH.
  2. In the Ports panel, forward 4200, 3000, and 8085.
  3. Open http://localhost:4200 in the VS Code browser or your regular browser. Services still run in Docker on EC2.
  4. Keep the SSH connection open while testing; use the forwarded address shown by VS Code if it selected a different local port.
Production needs a different setup: HTTPS and a real hostname/reverse proxy, browser API URLs for that hostname, matching CORS origins, and Secure cookies. Keep Postgres and Kafka private.
01

End-to-end request path

The UI calls Auth and Trade API directly from the browser; database and Kafka traffic stays on the Docker network.

  1. Register/login: Auth stores auth.users, creates trading.account, returns an access JWT, and stores a hashed refresh token.
  2. Place order: Trade API inserts trading.orders with NEW status and publishes ORDER_PLACED to Kafka topic orders.
  3. Executor consumes the event, fetches a Fauxnance quote, then fills/rejects the order and updates account/holding rows.
  4. Executor publishes TRADE_EXECUTED or TRADE_REJECTED to trade-events.
  5. DuckDB ETL reads Postgres periodically; the analytics frontend reads the shared DuckDB file.

Postgres inside Docker

Run from the EC2 host. You can also enter the database container and start psql directly.

EC2 HOST / OPEN PSQL
docker exec -it trading-postgres psql -U postgres -d trading_system_db
PSQL / LIST SCHEMAS AND TABLES
\conninfo
\dn
\dt auth.*
\dt trading.*
\d+ auth.users
\d+ auth.refresh_token
\d+ trading.account
\d+ trading.holding
\d+ trading.instrument
\d+ trading.orders
Privacy: never select password_hash or token_hash. This schema has no login-attempt history table; refresh_token rows are session metadata.
PSQL / COUNTS FOR ALL CORE TABLES
SELECT 'auth.users' AS table_name, COUNT(*) AS rows FROM auth.users
UNION ALL SELECT 'auth.refresh_token', COUNT(*) FROM auth.refresh_token
UNION ALL SELECT 'trading.account', COUNT(*) FROM trading.account
UNION ALL SELECT 'trading.holding', COUNT(*) FROM trading.holding
UNION ALL SELECT 'trading.instrument', COUNT(*) FROM trading.instrument
UNION ALL SELECT 'trading.orders', COUNT(*) FROM trading.orders
ORDER BY table_name;
PSQL / USER, ACCOUNT, HOLDING, REFRESH SESSION
SELECT u.user_id, u.username, u.email, u.created_on,
       a.account_id, a.status, a.currency, a.cash_balance
FROM auth.users u JOIN trading.account a USING (user_id)
WHERE u.username = 'YOUR_USERNAME';

SELECT ticker, quantity, average_price, as_of_date
FROM trading.holding WHERE account_id = 5 ORDER BY ticker;

SELECT rt.refresh_token_id, u.username, rt.created_on, rt.expires_at, rt.revoked_on
FROM auth.refresh_token rt JOIN auth.users u USING (user_id)
WHERE u.username = 'YOUR_USERNAME' ORDER BY rt.created_on DESC;
PSQL / FIND ALL ORDERS FOR A USER
SELECT o.order_id, u.username, o.account_id, o.ticker, o.side,
       o.quantity, o.order_type, o.status, o.price,
       o.executed_price, o.rejection_reason, o.received_at, o.executed_on
FROM trading.orders o
JOIN trading.account a USING (account_id)
JOIN auth.users u USING (user_id)
WHERE u.username = 'YOUR_USERNAME'
ORDER BY o.received_at DESC;

EC2 HOST / FIND A GOOG ORDER OR TRADE EVENT
for topic in orders trade-events market-data; do
  echo "=== $topic / GOOG ==="
  docker exec trading-kafka /opt/kafka/bin/kafka-console-consumer.sh \\
    --bootstrap-server localhost:9092 --topic "$topic" \\
    --from-beginning --max-messages 1000 --timeout-ms 15000 2>/dev/null \\
    | grep -F 'GOOG' || echo "No GOOG message found in $topic"
done
EC2 HOST / EXECUTOR CONSUMER LAG
docker exec trading-kafka /opt/kafka/bin/kafka-consumer-groups.sh \\
  --bootstrap-server localhost:9092 --group trade-executor --describe

Your GOOG test appeared in orders as ORDER_PLACED and in trade-events as TRADE_EXECUTED, order 19, filled at 337.32. A GOOG record in market-data is not expected until its publisher is fixed.

06

How Kafka infrastructure is created

The root stack uses one Kafka 3.8 KRaft broker (no ZooKeeper) and a one-shot topic initializer.

  1. Compose starts Kafka and waits until the broker health check passes.
  2. kafka-init waits for broker health, then creates topics with --create --if-not-exists.
  3. It creates orders (3 partitions, 7 days), trade-events (3 partitions, 30 days), market-data (6 partitions, 1 day), plus one matching .DLT topic for each.
  4. Trade API and executor start after the one-shot initializer exits successfully; auto topic creation is disabled.
CHECK THE INITIALIZER AND TOPICS
docker-compose ps
docker-compose logs kafka-init
docker exec trading-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

infra/scripts/create-topics.sh is an additional manual, idempotent script. Run from the repo root on EC2; it uses docker exec as a fallback:

EC2 HOST / MANUAL SCRIPT
bash infra/scripts/create-topics.sh
Name difference: root Compose creates the six .DLT topics. The manual script also creates legacy hyphenated names such as orders-dlt.

08

How environment variables load

Compose reads the root .env for substitutions, then passes only variables declared in each service's environment.

  1. Copy .env.example to an ignored root .env, then set local DB values, JWT secret, and a real Fauxnance key/base URL.
  2. Compose substitutes ${NAME} at container creation. A shell variable can override the file.
  3. Java/Spring maps container variables through application.yml; NestJS reads process.env; Flask reads os.getenv.
  4. Changing .env does not update an existing container; recreate affected services.
SAFE CONFIG CHECK / DOES NOT PRINT THE KEY
[[ -f .env ]] || cp .env.example .env
# Edit .env; never put secrets in this HTML or Git.
docker-compose up -d --force-recreate auth-service trade-api executor frontend
docker exec trading-executor sh -c 'test -n "$FAUXNANCE_API_KEY" && echo "Fauxnance key is set"'
Secrets: use unique production DB/JWT secrets and managed secret injection. Do not publish resolved docker-compose config output; it may reveal values. Root Compose hardcodes internal DB host postgres; a host export alone does not switch the stack to RDS.
09

ETL and analytics flow

The repository has more than one ETL entry point. Only the executor's DuckDB trigger is started by the root Compose stack.

  1. With ETL_ENABLED=true, Spring's executor startup runner launches etl_trigger_service.py.
  2. The trigger runs an initial pass, then repeats every ETL_REFRESH_INTERVAL_SECONDS (45 seconds by default).
  3. Pipeline reads Postgres orders/accounts/instruments from trading, initializes DuckDB date/dimension tables, then loads facts after its watermark.
  4. Rows are validated and deduplicated by source order ID; invalid rows are recorded for investigation; watermark advances after the pass.
  5. Executor writes /data/analytics.duckdb; Compose mounts the same named analytics_data volume in the frontend.
ETL / SETTINGS, LOG, SHARED FILE
docker exec trading-executor sh -c 'printf "ETL_ENABLED=%s\\nETL_REFRESH_INTERVAL_SECONDS=%s\\nDUCKDB_PATH=%s\\n" "$ETL_ENABLED" "$ETL_REFRESH_INTERVAL_SECONDS" "$DUCKDB_PATH"'
docker exec trading-executor tail -n 80 /app/etl_trigger_service.log
docker exec trading-frontend python -c 'import os; p="/data/analytics.duckdb"; print("exists:", os.path.exists(p), "bytes:", os.path.getsize(p) if os.path.exists(p) else 0)'

etl/duckdb_loader.py is a separate standalone Postgres-to-DuckDB loader. etl/main.py is a separate Kafka trade-event aggregation consumer. Neither is a root Compose service.

01

Blueprint: one service, one image

The repo already has per-component Dockerfiles and a root Compose stack. Dockerfiles normally belong at the root of each component folder, not all together in the repository root.

  1. Choose a boundary: auth, trade API, executor, or frontend. Postgres and Kafka remain separate services.
  2. Put the Dockerfile next to component source and choose a context that contains every COPY input.
  3. Use multi-stage builds for compiled apps, minimal runtime dependencies, a non-root user, and the actual listening port.
  4. Pass runtime config at container start. Never bake passwords, JWT secrets, or API keys into image layers.
  5. Use Compose to put services on a private network; expose only ports needed from the host/browser.
  6. Build, run, inspect, push a versioned tag, pull it elsewhere, and verify the same health endpoint.
Build context rule: docker build -f path/to/Dockerfile -t name:tag CONTEXT. The final argument controls what files Docker can access.

06

JFrog Artifactory: create, push, pull

Create a local Docker repository in JFrog Platform; use its exact registry hostname/repository path in Docker commands.

  1. Open JFrog Platform Administration > Repositories and create a Local repository with package type Docker (example key: docker-local).
  2. Copy the Docker registry endpoint/prefix from your JFrog setup. Cloud and on-prem deployments may use different hostnames or reverse-proxy ports.
  3. Create a least-privilege user/access token with deploy and read permission for that repository.
  4. Authenticate with stdin, tag local images using the full repository path, push, then pull to verify.
JFROG / LOGIN AND PUSH
export JFROG_REGISTRY='your-company.jfrog.io'
export JFROG_REPO_KEY='docker-local'
export JFROG_USER='your-jfrog-user'
export VERSION=1.0.0
read -rsp 'JFrog access token: ' JFROG_TOKEN; printf '\\n'
printf '%s' "$JFROG_TOKEN" | docker login "$JFROG_REGISTRY" --username "$JFROG_USER" --password-stdin
unset JFROG_TOKEN

for image in etp-trade-api etp-auth-service etp-executor etp-frontend; do
  docker tag "$image:$VERSION" "$JFROG_REGISTRY/$JFROG_REPO_KEY/$image:$VERSION"
  docker push "$JFROG_REGISTRY/$JFROG_REPO_KEY/$image:$VERSION"
done
JFROG / PULL
docker pull "$JFROG_REGISTRY/$JFROG_REPO_KEY/etp-trade-api:$VERSION"
docker pull "$JFROG_REGISTRY/$JFROG_REPO_KEY/etp-auth-service:$VERSION"
docker pull "$JFROG_REGISTRY/$JFROG_REPO_KEY/etp-executor:$VERSION"
docker pull "$JFROG_REGISTRY/$JFROG_REPO_KEY/etp-frontend:$VERSION"
docker logout "$JFROG_REGISTRY"
Registry path varies by JFrog configuration. Use the exact Docker endpoint from your admin/repository setup. Do not add https:// to docker login.

Amazon ECR: create, push, pull

Use an approved AWS IAM role, SSO identity, or credential provider with ECR permissions.

AWS / IDENTITY AND REPOSITORY CREATION
export AWS_REGION=eu-west-2
aws sts get-caller-identity
AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
ECR_REGISTRY="$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com"

for repo in etp-trade-api etp-auth-service etp-executor etp-frontend; do
  if ! aws ecr describe-repositories --region "$AWS_REGION" --repository-names "$repo" >/dev/null 2>&1; then
    aws ecr create-repository --region "$AWS_REGION" --repository-name "$repo" --image-scanning-configuration scanOnPush=true
  fi
done
AWS ECR / LOGIN AND PUSH
aws ecr get-login-password --region "$AWS_REGION" | docker login --username AWS --password-stdin "$ECR_REGISTRY"
for image in etp-trade-api etp-auth-service etp-executor etp-frontend; do
  docker tag "$image:$VERSION" "$ECR_REGISTRY/$image:$VERSION"
  docker push "$ECR_REGISTRY/$image:$VERSION"
done
AWS ECR / PULL
# Authenticate with the ECR login command above on this host first.
docker pull "$ECR_REGISTRY/etp-trade-api:$VERSION"

08

Pull, deploy, verify, roll back

Pushing stores an image; deployment hosts still need to pull it, configure runtime values, and start services.

  1. Use immutable version tags or commit SHAs, not only latest.
  2. Authenticate to the registry and pull the exact image version on the target host.
  3. In a deployment Compose file, use the full registry URI under image: instead of a local build: block.
  4. Inject runtime settings/secrets, start the stack, inspect status/logs, and check health.
  5. Keep the previous known-good tag for rollback; do not run the Sprint 6 and root stacks together.
VERIFY RELEASE
docker image inspect "$ECR_REGISTRY/etp-trade-api:$VERSION"
docker-compose pull
docker-compose up -d
docker-compose ps
docker-compose logs --tail=100 trade-api
curl -i http://localhost:8085/health
Security: never expose Postgres/Kafka publicly; use TLS, least privilege, managed secrets, image scanning, backups, and a rollback plan.
